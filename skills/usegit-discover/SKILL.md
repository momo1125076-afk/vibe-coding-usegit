# UseGit 需求访谈

将用户的想法转成后续搜索、选型、开发和验收都能使用的需求。使用用户的语言交流；替用户整理工程细节，保留用户对业务结果的决定权。

阶段名：`discover`。只在当前项目的 `.usegit/artifacts/` 写产物；由主 Skill `vibe-coding-usegit` 记录阶段状态，不直接修改调度状态文件。

## 输入

- 当前请求、已经确认的上下文、用户明确提供或允许使用的文档与示例。
- 如果存在，读取之前的需求、验收清单、约束、授权范围和待办问题。
- 收到主 Skill 的任务时，保留其 `project_root`、本次目标和已确认范围。

按需读取 [访谈提纲](references/interview-guide.md)。写产物前读取 [需求与交接格式](references/brief-contract.md)。

## 执行

### 1. 先复用已知信息

用一句话提炼“谁，在什么情况下，用什么功能，获得什么结果”。区分用户原话、文件证据和你的假设。文件需求保留出处；表格需求保留工作表、行号或原需求编号，不用自己的摘要覆盖原文。

已经清晰的需求直接整理并推进。不要把“复述后再确认”设成每个任务的前置手续。遇到旧要求与新要求冲突，采用最新明确指令并记录变更。

### 2. 只问会改变方案的问题

每轮最多问 1～3 个关键问题，优先解决目标平台、核心业务规则和必须满足的限制。给客户可理解的选项及其影响，例如“所有人共用一份库存”与“每个人只管理自己的库存”。

低影响信息先标成假设并继续；无法决定的高影响问题标成待定，不擅自替用户决定。等待回答时，继续不受该问题影响的资料整理或只读研究。只有缺失信息使当前阶段无法形成可执行目标时，才将该阶段记为 `blocked`。

### 3. 拆出真实流程和第一版范围

梳理角色、当前做法、痛点、成功条件和主要操作流程。区分“第一版必须有”“可以稍后补”“明确不做”，让每项需求对应一个业务结果。

同时记录：

- 平台和设备：微信内打开、浏览器、安装 App、桌面程序、后端服务等；允许一个项目包含多个端。
- 数据：来自哪里、谁能看和改、是否离线、是否同步、是否需要导入导出和备份。
- 集成：登录、支付、消息、地图、文件、企业系统、AI 模型或硬件；区分真实接入与演示替代。
- 交付：客户期待的访问地址、体验版本、安装包或源码；维护人、时间目标、预算范围和已有资源。

不要把“手机可以打开网页”直接等同于微信小程序或原生 App。涉及具体平台限制时交给平台路线核对，不凭经验承诺可以发布。

### 4. 写成可验收的需求

为需求分配稳定编号 `REQ-001`、`REQ-002`，为验收项分配 `REQ-001-A1` 等编号。用“已有条件 / 执行动作 / 预期结果”（Given / When / Then）写验收。

核心流程同时考虑成功、失败、重复操作、权限和恢复；仅在需求涉及相应能力时添加离线、并发、支付、同步或硬件验收。不要把“页面有一个按钮”当作该功能已实现。

性能、费用、工期、支持设备等可量化条件没有依据时标成建议或待定，不能写成客户已承诺的数字。此阶段只是定义验收，不将尚未执行的功能检查标为通过。

### 5. 交接并继续

输出需求说明、结构化需求和阶段报告。为 `usegit-find-skills` 提供能力缺口，为 `usegit-find-repos` 提供业务关键词、目标项目类型和硬条件；由主 Skill 决定并行或顺序调度。

通过 Skill 的 `name` 调用其他技能；必要时从当前技能目录清单按 frontmatter 查找，不假定兄弟目录名称或安装路径永远不变。无法调用子代理时，由当前 Agent 按相同职责顺序执行，不伪造并行执行记录。

## 输出

| 文件 | 内容 |
|---|---|
| `.usegit/artifacts/brief.md` | 面向客户的目标、角色、流程、首版范围、非目标、假设和待定问题 |
| `.usegit/artifacts/requirements.json` | 稳定需求编号、来源、优先级、平台、验收条件和依赖 |
| `.usegit/artifacts/discover.json` | 统一阶段结果、产物列表、需求来源证据、阻塞和下一步 |

统一阶段报告的必填字段为 `schema_version: 1`、`stage: "discover"`、`status`、`summary`、`outputs`、`evidence`、`checks`、`blockers`、`executed_actions`。本阶段 `status` 取 `complete`、`blocked` 或 `failed`，不能跳过。证据类型取 `file`、`command`、`url` 或 `manual`，验证状态取 `observed`、`simulated` 或 `not-run`。需求阶段尚未实施业务功能时，`checks` 保持空数组；待实施的验收条件记录在 `requirements`，后续运行和验收阶段再填写真实检查结果。不要将未来功能的未测状态混入已完成的需求阶段。

`discover.json` 顶层另需 `requirements` 数组，至少 1 项且 ID 唯一；每项包含 `id`、`priority: must|should|could`、`text`、`acceptance`（可观察结果或 Given/When/Then 字符串）。其 ID 必须与详细需求文件及所有后续 `checks.requirement_id` 对应。

`complete` 表示目标、首版主要流程、平台约束和验收定义足够支持下一步；它不代表功能已实现。无须等所有低影响假设得到回答才完成需求阶段。

## 范围变化与失败处理

- 新增平台、支付方式、数据去向或核心业务规则时，记录变更前后、受影响需求和需重跑阶段，交回主 Skill 使相关结果过期。不能沿用已经失效的选型或测试结论。
- 用户只要求调研时，交付需求与研究边界；不要把它扩大为安装、付费或正式发布的授权。
- 用户已经授权的行为继续执行，不重复索取相同授权。需要额外授权时先完成可审查的方案，只说明新增动作和影响。
- 资料缺失、冲突或不可访问时，保留已完成内容并写具体阻塞及下一步，不编造客户回答。
- 与客户讨论指当前对话中的协作。没有明确发送授权，不自动给客户发邮件、消息或邀请。
