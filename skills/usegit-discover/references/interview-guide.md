# 需求访谈提纲

## 阅读顺序

先读“问题选择”，再只读当前场景相关的主题。这里是 Agent 的备选问题库，不是一张必须全部问完的问卷。

## 问题选择

先整理已有答案。给剩余问题分别判断“是否改变选型”“是否阻止验证”“是否可以先用假设推进”。每轮选影响最大的 1～3 个，说明为什么需要知道。

| 情况 | 下一步 |
|---|---|
| 用户已给出明确目标、平台和主要功能 | 形成需求记录，直接进入搜索 |
| 用户只说“我想做一个管理系统” | 先问谁用、目前如何处理、最希望解决的一个问题 |
| 某个细节尚不清楚但不影响主体 | 写出暂定假设，继续不依赖它的工作 |
| 两种答案会导向完全不同的产品 | 问一个带影响说明的选择题 |
| 用户说“先做演示” | 明确演示可用的假数据边界和后续真实接入点 |
| 用户说“直接按你的判断做” | 记录选择理由与假设，尊重已给的预算、平台和发布边界 |

提问示例：“库存是你自己使用，还是几个人共同维护？这会影响是否需要登录、共享数据和权限。”避免只问“要不要多租户架构”。

## 业务与用户

| 要弄清什么 | 客户容易回答的问法 | 写入需求的内容 |
|---|---|---|
| 真正使用者 | 谁每天会用它？谁负责管理？ | 用户角色、权限边界 |
| 当前流程 | 现在这件事从开始到结束怎么做？ | 当前流程、工具和交接点 |
| 主要痛点 | 最容易漏掉或最耗时间的是哪一步？ | 问题与优先级依据 |
| 成功条件 | 上线后，什么变化会让你觉得值得做？ | 可观察的业务结果 |
| 使用频率 | 一天大约处理多少次？什么时间最集中？ | 容量假设与测试场景 |
| 例外情况 | 取消、重复、填错、网络断了时，通常怎么处理？ | 失败、撤销与恢复规则 |

当用户的方案只是实现手段时，追问目标。例如“想做一个二维码”，继续了解扫码后究竟要预约、领资料还是支付。

## 平台与入口

从使用场景选择候选平台，不要求客户先选技术框架。

| 客户的说法 | 需要进一步判断 |
|---|---|
| 发一个链接，大家都能打开 | 手机/电脑浏览器、响应式布局、外网或内网、是否需登录 |
| 在微信里直接预约 | 微信小程序还是 H5；是否需要微信身份、支付、订阅消息等 |
| 没网也能查、拍照记录 | 本地存储范围、离线首次启动、照片持久化、是否需要同步 |
| 安装到 Windows/Mac | 目标系统和最低版本、安装升级、文件或串口等本地能力 |
| 以后也要上 iPhone 和安卓 | 各平台必须实现的能力、分发方式、签名与账号是否具备 |
| 只给内部员工用 | 内网可达性、身份系统、权限、数据保留和维护责任 |
| 连接蓝牙或其他设备 | 设备型号、协议资料、可提供的测试设备、断连处理 |

平台标识使用主项目支持的值：`web`、`pwa`、`wechat-miniprogram`、`other-miniprogram`、`ios`、`android`、`desktop`、`backend`、`browser-extension`、`automation`、`ai-service`、`game`、`iot`。这里只记录需求，具体技术路线由选型阶段核实。

## 功能与数据

按功能相关性补充，不把每项都默认加入项目。

| 能力 | 必须说清楚的业务问题 |
|---|---|
| 登录与角色 | 谁需要登录，谁能查看或修改什么，管理员如何交接？ |
| 支付 | 收什么费用、何时扣款、退款规则、测试阶段是否真实收款？ |
| 预约与订单 | 是否有容量、时间冲突、取消、退款或管理员改期？ |
| 文件与导入 | 现有资料是什么格式，重复数据怎么办，失败如何重试？ |
| 搜索与统计 | 用户通过什么找到记录，统计口径由谁决定？ |
| 消息提醒 | 提醒谁、什么时候、通过什么渠道，失败能否手动补发？ |
| 离线与同步 | 哪些功能必须离线，多个设备同时修改时如何处理？ |
| AI 功能 | 输入什么、输出供谁使用、能否发送到外部模型、错误如何纠正？ |
| 外部系统 | 是否有接口文档、测试账号或沙箱，哪些工作需要对方配合？ |
| 硬件 | 协议和真实设备是否可用，模拟与真机验证分别验收什么？ |

不要求客户在聊天中提供密码、令牌、支付私钥等凭据。记录“需要配置哪项、由谁配置”，把凭据留在平台授权或安全配置渠道。

## 首版范围与交付

为首版选择一个能独立完成的业务闭环。例如预约系统的首版可以是“用户选时段 → 提交预约 → 管理员查看 → 用户取消”；会员积分、营销海报等如果不影响这一闭环，可放到后续版本。

预算分开记录开发投入、持续运行费用、第三方接口费用。仅记录客户给出的范围；需要估算时提供假设和可替代方案，不承诺未核实的价格或平台审核时长。

交付方式使用客户能够核对的说法：

- “在指定手机上可以安装并离线运行”。
- “指定员工能打开内网地址完成审批”。
- “上传到小程序体验版，并完成列出的测试”。
- “已提交审核”与“已经对外发布”分别记录。

## 验收写法

先选可观察的结果，再决定验证方法。

| 原始说法 | 可验收的表达 |
|---|---|
| 预约要好用 | 已有空闲时段，用户提交预约后得到编号，管理员能看到同一条记录 |
| 不能重复预约 | 同一时段容量已满，另一位用户提交时收到明确提示，剩余容量保持正确 |
| 要能离线用 | 手机断网且重启 App 后，已保存的记录与照片仍能打开，并可继续新增 |
| 权限要分开 | 普通员工无法查看另一部门的受限记录，直接访问对应接口也被拒绝 |
| 要方便升级 | 安装新版本后，旧版本已有数据仍在，主要流程能够继续使用 |

列出验收的环境和数据边界。使用模拟接口得到的结果只能证明模拟流程，不证明真实支付、微信能力或硬件已接通。

## 范围变化

收到新要求时，保留旧编号，将删除的需求标为取消，不重新编号已有需求。新增一条变更记录：新要求、来源、受影响需求、实现影响、验证影响和需重跑的阶段。

先处理与本轮目标相关的变更，避免顺手把后续想法全部放进当前版本。
