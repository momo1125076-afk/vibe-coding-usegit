# UseGit 项目改造

在可复现基线上实现需求差异，优先复用项目已有能力。以用户能完成的任务安排开发顺序。

## 接收输入

读取需求清单、范围与验收条件、选型决策、运行基线 `.usegit/artifacts/run.json`、目标平台、已有授权与当前工作区改动。按名称接收主技能 `vibe-coding-usegit` 的上下文；独立调用时从现有项目文件补齐，不依赖固定兄弟目录。

按需读取 [改造与跨端检查](references/adaptation.md)。如果基线运行受阻，先解决阻塞或明确哪些改动可独立进行，不把“没试过的原项目”当作已知可靠基线。

## 执行

1. **列出差异。** 将每个需求编号对应到原项目已有能力、需要修改的文件/模块、目标平台和验收步骤。保留不确定项，检查许可证和资源使用条件，不删除上游版权或误称全部原创。
2. **先跑通一条业务链。** 按“界面入口 → 业务规则 → 数据保存 → 失败提示 → 验收”拆成小步。先交付最小可用版本，再处理次要功能。客户用日常语言说需求；技术选择由 Agent 根据证据解释。
3. **限制改动范围。** 沿用已有框架和锁文件；需要换栈、数据库迁移或引入服务时说明它解决的具体问题。准备迁移与回退方案，保护已有用户数据；不为了统一风格大面积改写无关模块。
4. **分离共用与平台差异。** 复用业务规则和数据契约，对登录、支付、相机、文件、通知、定位、蓝牙、离线等能力建立逐平台适配与验证记录。不要把相同的按钮外观当作相同的底层能力。
5. **补齐产品状态。** 覆盖加载、空数据、错误、权限拒绝、断网、重复提交、恢复和更新后的数据兼容性。第三方依赖失败时提供与业务相称的退路；不悄悄切到会泄露数据或增加费用的服务。
6. **验证本步改动。** 运行现有相关测试和最小真实业务检查。仅为具体风险增加必要测试。使用替身、模拟支付或假数据时写清覆盖边界，不据此宣布正式能力可用。
7. **收敛交付。** 记录改动、需求映射、配置变化、已测范围和剩余问题。默认 `local` 模式交给 `usegit-verify`；`preview / release` 模式交给 `usegit-deploy`。架构与候选项目根本不匹配时，带证据回到 `usegit-evaluate`，不要在错误方案上持续叠补丁。

## 协作与沟通

把互不写同一文件的任务交给协作 Agent，约定输入、输出与文件范围；由一个集成者合并、检查冲突和执行最终测试。任务可并行，状态登记与发布保持一个负责人。

复用已有确认和授权，不逐步重复征求许可。只有新增需求改变成本、平台、数据处理或发布范围时，先写出影响与建议，再确认差额。客户未要求发送时只形成讨论稿，不向客户、团队或外部系统发送消息。

## 输出与完成条件

写入 `.usegit/artifacts/adapt.json` 和客户可读的 `adapt.md`，并保留 `.usegit/evidence/adapt/` 中实际执行的证据。JSON 使用统一字段 `schema_version: 1`、`stage: "adapt"`、`status`、`summary`、`outputs`、`evidence`、`checks`、`blockers`、`executed_actions`；可以增加 `changes`、`requirement_mapping` 和 `decisions`。

- 记录当前 commit 和未提交改动；真实运行证据使用 `verification: "observed"`，命令附退出码和日志路径。
- `checks` 对应需求编号，引用本次真实 `evidence_ids`，区分 `pass / fail / not-run / blocked / not-applicable`。
- 只有约定改造范围已实现且本步必要验证通过才标 `complete`；剩余必需项受外部条件限制写 `blocked`，已执行但未修好写 `failed`。
- 原方案已完全满足需求、确实无需改造时，可用带依据的 `skipped`；不要为了走流程制造代码变更。
- 不直接修改调度状态文件；将产物交回主技能登记。
