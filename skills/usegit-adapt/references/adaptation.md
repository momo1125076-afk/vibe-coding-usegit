# 改造与跨端检查

## 需求到实现的映射

为每个需求维护一行：需求编号、用户场景、已有能力、修改位置、数据变化、目标端、外部依赖、验收步骤、证据和状态。多平台需求分别列状态，避免“Web 完成”覆盖“小程序未测”。

优先完成能展示真实价值的垂直小步。例如预约应用先完成选择时段、提交、查看结果和取消，再补报表；不要先堆满菜单却没有可用业务。

## 常见能力拆解

| 客户说法 | 实现时需要澄清或验证的内容 |
|---|---|
| 可以登录 | 哪些用户、身份来源、退出与过期、是否需要角色；微信登录与普通网页登录分开接入 |
| 可以付费 | 商品/订单规则、服务端状态、重复通知、取消/失败、退款；模拟结果不代表真实收付款通过 |
| 不用网络也能用 | 哪些内容本地保存、首次启动是否依赖下载、断网写入、恢复联网后的冲突、导出/恢复 |
| 多端都能用 | 共用数据和规则，逐端检查导航、输入、权限、第三方 SDK 与构建产物 |
| 可以接 AI | 数据来源、允许发送到哪里、模型/接口、失败与限流、费用约束、是否真的离线推理 |
| 连硬件 | 型号与协议、端口/蓝牙权限、断连重连、异常报文、真实设备或模拟器覆盖范围 |

## 跨端选择

保留所选项目已有技术栈，除非功能或维护证据表明需要调整。uni-app、Taro、Flutter、React Native 是可评估的路线，不是“一个项目自动覆盖所有平台”的保证。原生插件、支付和登录等差异应成为选型条件与验收项。

uni-app 的条件编译区分平台代码，Taro 的构建明确选择目标端；采用它们时记录项目支持的具体目标、版本和已验证插件，而不是只记录框架名。

- [uni-app 条件编译](https://uniapp.dcloud.net.cn/tutorial/platform)
- [Taro 编译与目标端](https://docs.taro.zone/docs/GETTING-STARTED)

资料核对日期：2026-11-04。框架升级或平台政策变化时重新检查。

## 故障处理

先复现最小失败，判断是上游原有问题、本次改动还是平台配置。记录最后已知可用 commit。恢复代码不能自动恢复数据库；有数据结构变化时单独检查兼容性。使用主调度的重试预算，持续失败时缩小问题或回到选型，不无限循环改写。
