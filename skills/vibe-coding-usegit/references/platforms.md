核对日期：2026-11-04。这里定义 UseGit 的任务分流和验收要求；它不是已经实测全部平台的兼容性声明。执行具体项目时重新核对上游版本、官方发布要求与当前工具能力。

## 先确定交付范围

1. 先问用户在哪里使用：浏览器、微信、手机安装、电脑安装、API、设备等。若已有明确指示，直接沿用。
2. 一个产品可包含多个目标，例如 `wechat-miniprogram + backend + web`；为每个目标分开记录功能、构建、发布和验证状态。
3. 只询问影响路线的缺失信息，例如是否必须离线、是否使用支付/蓝牙、目标用户和已有账号。不要在开始前要求客户填写完整技术问卷。
4. 先做环境检查，再决定能执行到哪里；本机没有原生工具或设备时，继续能独立完成的源码与文档工作，保留具体阻塞。

| 模式 | 做到哪里 | 发布处理 |
|---|---|---|
| `plan` | 需求、技能发现、项目搜索与比较 | 不运行项目，不发布 |
| `local`（默认） | 在当前授权环境运行、改造并验证 | 不要求云部署，`deploy` 不属于必经阶段 |
| `preview` | 在明确的预览/测试环境运行并验收 | 使用已有授权；预览可能具有公开 URL，核对受众 |
| `release` | 达到用户指定的正式交付范围并验证 | 复用明确授权；新增公开范围、费用或商店提交先确认差额 |

## 平台路线表

这些是研究时的候选方向，选型以需求、现有仓库和可运行证据为准。不要只因为“跨端”就选择一个框架覆盖所有目标。

| 平台 ID | 用户通常怎么描述 | 可评估路线 | 应交付的东西 | 关键依赖与验证 |
|---|---|---|---|---|
| `web` | 网站、H5、手机网页、PC 后台、Web App | 沿用合适的 Web 项目；静态前端、服务端渲染或前后端分离按需要选择 | 可运行代码与构建产物；需上线时给实际地址 | 响应式布局、路由刷新、浏览器、API 与持久化；手机浏览器不等于 App |
| `pwa` | 能装到桌面的网页、轻量离线工具 | 在适配的 Web 项目上实现 manifest、缓存/更新与安装体验 | 可安装 Web 应用及承诺的离线能力 | HTTPS/本地开发环境、目标浏览器；安装、断网、更新分别验证 [S4] |
| `wechat-miniprogram` | 微信里打开、扫码使用、微信登录/支付 | 微信原生、合适的 uni-app/Taro 项目，按能力评估 CloudBase 或独立后端 | 小程序目标代码、开发工具检查记录、授权范围内的预览/上传/发布回执 | AppID、对应工具、服务端、域名、必要密钥与后台配置；各发布阶段分开 [S1–S3,S12] |
| `other-miniprogram` | 支付宝/抖音/飞书等小程序 | 先指定具体宿主，再检查原生或跨端插件支持 | 对应宿主构建与测试记录 | 独立账号、API、权限、审核入口；不能复用微信验收结论 [S2,S3] |
| `ios` | iPhone/iPad 上安装、TestFlight、App Store | 合适的 Flutter、React Native、uni-app 或原生项目 | 目标构建、测试分发或约定发布材料 | macOS/Xcode 或相应构建服务、签名、分发账号；模拟器/真机/商店状态分开 [S5,S7] |
| `android` | 安卓安装包、安卓应用市场 | 合适的 Flutter、React Native、uni-app 或原生项目 | 按用途生成 APK/AAB 等目标产物 | Android 工具链、签名、应用 ID、安装与升级；具体商店要求执行时核对 [S6,S7] |
| `desktop` | Windows/macOS/Linux 安装软件 | Electron、Tauri 或适用的原生项目 | 指定 OS/架构的安装包、更新/卸载说明 | 对应构建/测试环境、必要签名，干净安装与升级；分别记录三类系统 [S8,S9] |
| `backend` | API 服务、后台管理的数据层、SaaS | 适合业务的服务端项目与数据库；使用已选部署平台或自托管 | API、数据库迁移、启动配置、部署与恢复说明 | 鉴权、持久化、任务、备份和真实请求；管理界面可另设 `web` |
| `browser-extension` | 浏览器插件、侧栏、网页辅助 | 与目标浏览器兼容的扩展项目 | 扩展包、加载说明、约定的商店材料 | manifest、最小必要权限、真实加载与功能测试；商店提交单列 [S10] |
| `automation` | 批处理、脚本、CLI、定时任务、工作流 | 现成脚本/工作流项目或小型自建工具 | 可执行工具、输入输出示例、调度和停用说明 | 运行账号、文件权限、幂等、失败重试；定时运行必须实际接入调度器 |
| `ai-service` | AI 助手、知识库、RAG、Agent、图像/视频流程 | 按任务搜索可运行项目、模型或服务，分离界面与推理 | 实际 AI 工作流、可追溯评测、模型/接口配置 | 模型与权重许可、数据流向、GPU/内存/API、费用、超时和限流；离线要求逐层验证 |
| `game` | H5 小游戏、Godot 游戏、多端试玩 | 与玩法及目标平台匹配的游戏框架/引擎项目 | 目标平台可玩构建、操作说明与资源来源 | 引擎、目标 SDK/导出模板、资源许可、输入、性能、存档；游戏可再关联 `web/ios/android/desktop` [S11] |
| `iot` | ESP32、串口、蓝牙、传感器或设备 App | 对应芯片/协议的固件、设备网关与界面项目 | 固件/工具、协议说明及实际联调记录 | 具体硬件、驱动、串口/蓝牙、恢复机制；无硬件只能完成软件侧验证 [S13] |

如需鸿蒙原生 App、企业专有小程序宿主或其他新平台，记录新目标与官方支持依据，交回需求/选型阶段扩展；不要把某个 WebView 或元服务目标自动当作完整原生支持。

## 客户需求到功能拆解

从客户实际工作提问，并把答案转为可验收需求。下列维度只在相关时展开。

| 维度 | 通俗问题 | 输出给开发/验收的内容 |
|---|---|---|
| 用户与角色 | 谁来用？普通用户和管理员分别能做什么？ | 用户角色、权限、核心任务与禁止动作 |
| 页面与操作 | 用户第一步点什么，做完会看到什么？ | 页面清单、入口、导航、表单、弹窗和结果状态 |
| 业务规则 | 哪些条件下能提交、取消、修改或退款？ | 正常/失败分支、状态流转、重复操作处理 |
| 数据 | 保存什么？多久保存？是否要导出、同步或离线？ | 字段、存储、备份、保留与恢复需求 |
| 登录与支付 | 必须用哪种身份？是否真实收款？ | 平台身份、服务端依赖、业务订单与验收环境 |
| 设备能力 | 是否需要相机、文件、定位、通知、蓝牙或串口？ | 逐端能力矩阵、权限、替代方案与真机要求 |
| AI 与内容 | AI 处理什么资料？可以发送给谁？失败怎么办？ | 模型/接口候选、数据边界、评测样本、费用与失败处理 |
| 多地区与可用性 | 面向哪里，哪些语言，网络不好时怎么办？ | 语言、时区、地区服务依赖、网络与性能目标 |
| 运维与交付 | 谁负责更新和查看数据？只要演示还是正式给客户用？ | 部署模式、管理入口、恢复方法、维护责任与授权范围 |

把每项需求写成可观察结果，例如“断网后仍能打开已保存物品并新增一条，重启不丢失”，不要只写“支持离线”。使用 `requirements[{id,priority,text,acceptance}]`，验证阶段必须覆盖所有 `must`。

## 微信小程序专线

### 区分三个工程对象

小程序前端负责微信里的页面与交互；后端处理业务、账户、订单等服务端逻辑；管理后台是可选的独立 Web 入口。项目可能同时包含三者，也可能需要组合多个仓库。比较开源项目时说明覆盖了哪一层，以及缺少哪一层。

### 区分发布节点

`编译目标代码 → 开发工具运行 → 预览/上传 → 体验测试 → 提交审核 → 审核结果 → 发布`

这个顺序是需要记录的阶段，不表示本项目会自动执行全部节点。官方 `miniprogram-ci` 提供预览/上传等能力，使用前需要合适的 AppID、项目路径、代码上传密钥和 IP 配置。[S1] 实际项目执行时查看当前 CLI 参数与版本；不要在公共配置里记录秘密。

### 分别处理平台能力

- 登录：明确微信身份与业务账户如何关联；缺少真实 AppID 或服务端条件时记录未测部分。
- 支付：先核对对应商户产品与已授权环境，再实现订单与服务端状态；用模拟测试支持开发，正式能力另验收。[S14]
- 网络与文件：按实际 API 核对域名、HTTPS 与访问权限；不能用开发工具关闭校验的结果证明体验版可用。[S12]
- 多端：uni-app/Taro 的 H5、微信和其他目标分开构建与验证；平台插件和 API 的适配情况是选型依据。[S2,S3]

## 多端项目选择

优先考虑满足需求的可维护项目，按现有团队能力和部署约束取舍：

- 微信为主要入口且业务较轻：优先搜索原生小程序和成熟跨端项目，检查后端是否齐全。
- 同时要小程序与 H5：比较跨端项目的现成适配质量，逐项验证差异能力。
- 需要手机原生能力或复杂交互：比较移动框架与原生项目，核对必要插件、签名和设备验证条件。
- 需要本地文件/串口/桌面能力：将桌面应用作为真实目标；Web 页面可作原型但不能替代安装包。
- 离线优先：检查首次启动、资源下载、账号、模型和数据依赖；“能打开界面”不足以证明整个产品离线。

这些是 UseGit 的选型建议，不是某个框架在所有场景下更优的事实结论。

## 验证与阻塞

每个目标分别保存源码版本、环境、命令与退出码、日志、截图/回执/URL。记录 `observed / simulated / not-run`；只有真实证据支持的必需检查才可通过。缺少 Mac、开发者工具、签名、商户环境、审核或硬件时，用具体 blocker 说明下一步，不把 Web 演示或 mock 改写成原生成功。

`plan` 的交付是有证据的方案；`local` 的交付是在当前环境中确实运行的结果；`preview/release` 还需核对对应平台的真实部署/发布状态。不会仅因阶段定义存在就承诺可以在当前云电脑自动完成全部原生构建。
